# Introduction

Whenever users report a problem on a Linux system, the first responsibility of a Linux System Administrator is **to collect as much information as possible** before attempting to troubleshoot.

Examples include:

- What error occurred?
- When did it happen?
- Which service failed?
- Was the system recently rebooted?
- Are there any authentication failures?
- Are there any kernel errors?

Instead of guessing, administrators analyze the system logs to identify the root cause of the problem.

---

# Understanding Linux Logging

Linux has two primary logging services.

| Service | Purpose |
|----------|---------|
| `systemd-journald` | Collects and stores journal logs |
| `rsyslog` | Stores logs permanently in `/var/log` |

---

# systemd-journald vs rsyslog

| Feature | systemd-journald | rsyslog |
|----------|------------------|----------|
| Storage Location | Memory (RAM) by default | Disk |
| Persistent After Reboot | No (unless configured) | Yes |
| Tool Used | `journalctl` | `less`, `tail`, `cat` |
| Log Format | Binary | Plain Text |

---

# What is `journalctl`?

`journalctl` is the standard utility used to read logs collected by **systemd-journald**.

Since the journal is stored in binary format, it cannot be read using commands like `cat`.

Instead, Linux provides the `journalctl` command.

Basic syntax:

```bash
journalctl
```

This displays all available journal messages.

---

# Step 1 – Display All Journal Logs

```bash
journalctl
```

This command displays every journal message stored by `systemd-journald`.

---

# Step 2 – Display Current Boot Logs

To display messages generated since the current boot:

```bash
journalctl -b
```

Here:

- `-b` = Boot

This displays all messages generated after the system was last started.

---

# Step 3 – View Previous Boot Logs

To display logs from the previous boot:

```bash
journalctl -b -1
```

To display logs from two boots ago:

```bash
journalctl -b -2
```

You can specify any previous boot number.

---

# Step 4 – List Available Boots

Display every boot stored in the journal.

```bash
journalctl --list-boots
```

Example Output:

```text
-2
-1
 0
```

Where:

- `0` = Current Boot
- `-1` = Previous Boot
- `-2` = Two Boots Ago

---

# Step 5 – Follow Logs in Real-Time

To continuously monitor new log entries:

```bash
journalctl -f
```

or

```bash
journalctl -ef
```

Explanation:

- `-f` = Follow Mode
- `-e` = Jump to the End

This behaves similarly to:

```bash
tail -f
```

Whenever a new log entry is generated, it immediately appears on the screen.

# Step 6 – Display Logs for a Specific Service

To display logs generated by a specific systemd service:

```bash
journalctl -u sshd.service
```

or

```bash
journalctl --unit=sshd.service
```

This displays only SSH service logs.

Other examples:

```bash
journalctl -u NetworkManager.service
```

```bash
journalctl -u firewalld.service
```

```bash
journalctl -u crond.service
```

---

# Step 7 – Display Messages by Priority

Journal logs can also be filtered by severity.

Example:

```bash
journalctl -p err
```

Display only error messages.

---

## Priority Levels

| Priority | Meaning |
|-----------|---------|
| emerg | Emergency |
| alert | Alert |
| crit | Critical |
| err | Error |
| warning | Warning |
| notice | Notice |
| info | Information |
| debug | Debug |

---

## Display a Range of Priorities

Example:

```bash
journalctl -p err..alert
```

This displays:

- Error
- Critical
- Alert

messages only.

---

# Step 8 – Persistent Journal Logs

By default, `systemd-journald` stores logs inside memory.

This means:

- Reboot the system
- Old logs disappear

These are called:

> **Volatile Journal Logs**

---

## Persistent Journal

If journal storage is configured as persistent:

Logs are written to disk.

Advantages:

- Logs survive reboot.
- Previous boot logs remain available.
- Better for troubleshooting.

Persistent journal storage is normally located at:

```text
/var/log/journal
```

---

# Key Takeaways

- `journalctl` is used to read logs collected by **systemd-journald**.
- By default, journal logs are stored in memory and may not survive a reboot.
- Using persistent journal storage allows logs to remain available after a reboot.
- `journalctl` provides powerful filtering by:
  - Boot
  - Service
  - Priority
  - Time
- Real-time monitoring using `journalctl -ef` is extremely useful during troubleshooting.

---

# Remember

> **Think of `journalctl` as a search engine for Linux system logs.**
>
> Instead of manually searching through log files, `journalctl` allows you to quickly filter logs by:
>
> - Boot
> - Service
> - Severity
> - Time
>
> This makes troubleshooting much faster and more efficient.
