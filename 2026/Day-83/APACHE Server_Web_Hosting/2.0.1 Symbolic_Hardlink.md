# Linux Symbolic Links – Linking Across Partitions and Filesystems

> **Understanding Why Symbolic Links Can Cross Filesystem Boundaries While Hard Links Cannot**

---

* Understand the difference between a pathname and an inode reference.

# 📖 Introduction

Yes, a **symbolic link** can point to a file or directory located on a completely different filesystem or partition.

This is one of the major advantages of a symbolic link, also called a:

```text
Soft Link
```

over a:

```text
Hard Link
```

For example, suppose:

```text
/etc
```

is located on the root filesystem:

```text
/
```

while:

```text
/boot
```

is mounted from a separate partition.

A symbolic link stored under `/etc` can still point to a file located under `/boot`.

---

# Example Filesystem Layout

Suppose the system contains:

```text
/dev/sda2
   │
   ▼
Root Filesystem /
   │
   ├── /etc
   ├── /usr
   ├── /var
   └── /home
```

and another partition:

```text
/dev/sda1
   │
   ▼
/boot
```

Even though `/etc` and `/boot` are on different filesystems, a symbolic link can connect them.

---

# Example

Suppose this file exists:

```text
/boot/grub2/grub.cfg
```

You can create a symbolic link inside `/etc`:

```bash
ln -s /boot/grub2/grub.cfg /etc/grub2.cfg
```

Now:

```text
/etc/grub2.cfg
```

points to:

```text
/boot/grub2/grub.cfg
```

---

# Symbolic Link Flow

```text
Root Filesystem
/
│
├── etc
│    │
│    └── grub2.cfg
│           │
│           │ Symbolic Link
│           ▼
│
└───────────────► /boot/grub2/grub.cfg
                         │
                         ▼
                  Separate Filesystem
```

---

# Verify the Symbolic Link

Run:

```bash
ls -l /etc/grub2.cfg
```

Example output:

```text
lrwxrwxrwx 1 root root 22 Aug 16 10:25 /etc/grub2.cfg -> /boot/grub2/grub.cfg
```

The important part is:

```text
/etc/grub2.cfg -> /boot/grub2/grub.cfg
```

This tells you that `/etc/grub2.cfg` is pointing to the target file.

---

# Understanding the First Character

Notice:

```text
lrwxrwxrwx
```

The first character is:

```text
l
```

which means:

```text
Symbolic Link
```

Compare:

```text
-   Regular file
d   Directory
l   Symbolic link
```

---

# Why Can Symbolic Links Cross Filesystems?

A symbolic link does not point directly to the inode of the target file.

Instead, the symbolic link stores a:

```text
Pathname
```

For example:

```text
/boot/grub2/grub.cfg
```

The link essentially contains that path.

---

# Conceptual View

```text
/etc/grub2.cfg
      │
      ▼
Stores the text:
/boot/grub2/grub.cfg
      │
      ▼
Linux Resolves the Path
      │
      ▼
Target File
```

Because Linux resolves a pathname, the target can be located on another mounted filesystem.

---

# The Virtual File System Layer

Linux provides a layer known as:

```text
VFS
```

which means:

```text
Virtual File System
```

The VFS gives applications a unified view of files even when the files are stored on different underlying filesystems.

For example:

```text
/
│
├── /etc
│     └── Root filesystem
│
├── /boot
│     └── Separate filesystem
│
├── /home
│     └── Separate filesystem
│
└── /mnt/nfs
      └── Network filesystem
```

To applications and users, these all appear as part of one Linux directory tree.

---

# VFS Path Resolution

Suppose you access:

```bash
cat /etc/grub2.cfg
```

Linux sees:

```text
/etc/grub2.cfg
      │
      ▼
Symbolic Link
      │
      ▼
/boot/grub2/grub.cfg
      │
      ▼
VFS Resolves /boot
      │
      ▼
Separate Mounted Filesystem
      │
      ▼
Target File Opened
```

The fact that `/boot` is on another partition does not prevent the symbolic link from working.

---

# Symbolic Links Can Cross Many Storage Boundaries

A symbolic link can point across:

* Disk partitions
* Different filesystems
* LVM logical volumes
* Separate physical disks
* Mounted USB drives
* NFS mounts
* Other mounted network filesystems

Example:

```text
/root filesystem
      │
      └── /etc/my-link
                 │
                 ▼
          /data/application.conf
                 │
                 ▼
           Separate LVM Volume
```

---

# Example – Separate Data Filesystem

Suppose:

```text
/data
```

is another filesystem.

Create:

```bash
ln -s /data/config/app.conf /etc/app.conf
```

Now:

```text
/etc/app.conf
```

points to:

```text
/data/config/app.conf
```

even though the files are located on different filesystems.

---

# Symbolic Links Can Point to Directories

Another major benefit of symbolic links is that they can point to directories.

Example:

```bash
ln -s /data/webfiles /var/www/html/data
```

Now:

```text
/var/www/html/data
```

points to:

```text
/data/webfiles
```

---

# Directory Link Flow

```text
/var/www/html/data
        │
        │ Symbolic Link
        ▼
/data/webfiles
        │
        ▼
Separate Filesystem
```

Applications accessing:

```text
/var/www/html/data
```

are redirected to:

```text
/data/webfiles
```

---

# Symbolic Links and Unmounted Filesystems

A symbolic link can exist even when its target is unavailable.

Suppose:

```text
/data
```

is a separate filesystem and is currently not mounted.

You have:

```text
/etc/app-data -> /data/application
```

The symbolic link itself still exists.

However, the target cannot be reached.

---

# Example

```bash
ls -l /etc/app-data
```

may still show:

```text
/etc/app-data -> /data/application
```

But:

```bash
ls /etc/app-data
```

may fail because the target does not currently exist or the filesystem is not mounted.

---

# Dangling Symbolic Link

A symbolic link whose target does not exist is called a:

```text
Dangling Link
```

or:

```text
Broken Symbolic Link
```

Conceptually:

```text
Symbolic Link
     │
     ▼
Target Path
     │
     X
Target Missing
```

---

# Example

Create:

```bash
ln -s /data/file1 /tmp/file1-link
```

If:

```text
/data/file1
```

does not exist, then:

```text
/tmp/file1-link
```

still exists.

But attempting:

```bash
cat /tmp/file1-link
```

will fail.

---

# What About `/etc/fstab`?

The file:

```text
/etc/fstab
```

is normally stored on the root filesystem.

It contains information that tells Linux which filesystems should be mounted and where.

For example:

```text
UUID=xxxx-xxxx  /boot  xfs  defaults  0 0
```

This entry does not itself function as a symbolic link.

Instead, `/etc/fstab` tells the operating system:

> Mount this filesystem at `/boot`.

Once `/boot` is mounted, symbolic links elsewhere in the filesystem tree can point to files under `/boot`.

---

# `/etc/fstab` and `/boot` Relationship

```text
/etc/fstab
     │
     │ Defines Mount
     ▼
/dev/sda1
     │
     ▼
Mounted at /boot
     │
     ▼
/boot/grub2/grub.cfg
```

Then a symbolic link can reference it:

```text
/etc/grub2.cfg
      │
      ▼
/boot/grub2/grub.cfg
```

So these are two separate concepts:

```text
/etc/fstab
     │
     └── Defines filesystem mounts

Symbolic Link
     │
     └── References a pathname
```

---

# Why Hard Links Are Different

A hard link does not store a pathname to another file.

Instead, it creates another directory entry pointing to the same inode.

Conceptually:

```text
file1
   │
   └───────┐
           ▼
         Inode
           ▲
   ┌───────┘
   │
file1-hardlink
```

Both names reference exactly the same inode.

---

# Inode Example

Suppose:

```bash
echo "Linux Classes" > file1
```

Check the inode:

```bash
ls -li file1
```

Example:

```text
105678 -rw-r--r-- 1 student student 14 Aug 16 10:30 file1
```

Create a hard link:

```bash
ln file1 file1-hard
```

Check:

```bash
ls -li file1 file1-hard
```

You may see:

```text
105678 -rw-r--r-- 2 student student 14 Aug 16 10:30 file1
105678 -rw-r--r-- 2 student student 14 Aug 16 10:30 file1-hard
```

Both have:

```text
105678
```

as their inode number.

---

# Why Hard Links Cannot Cross Filesystems

Each filesystem maintains its own inode table.

For example:

```text
Filesystem A
/dev/sda2
     │
     ├── Inode 100
     ├── Inode 101
     └── Inode 102
```

and:

```text
Filesystem B
/dev/sda1
     │
     ├── Inode 100
     ├── Inode 101
     └── Inode 102
```

Even though the inode numbers may appear identical, they belong to different filesystems.

A hard link must reference an inode inside the **same filesystem**.

---

# Hard Link Limitation

```text
Filesystem A
      │
      ├── file1
      │      │
      │      ▼
      │    Inode 500
      │      ▲
      │      │
      └── hard-link
```

This works.

But:

```text
Filesystem A                  Filesystem B
    file1                         hard-link
      │                              │
      ▼                              X
   Inode 500  ◄──────────────────────┘
```

does not work.

---

# Example – Hard Link Across Partitions

Suppose:

```text
/root filesystem → /dev/sda2
/boot filesystem → /dev/sda1
```

Try:

```bash
ln /etc/hosts /boot/hosts-hardlink
```

If `/boot` is a separate filesystem, Linux will normally return:

```text
Invalid cross-device link
```

This is because a hard link cannot reference an inode located in another filesystem.

---

# Symbolic Link Across the Same Boundary

This works:

```bash
ln -s /etc/hosts /boot/hosts-softlink
```

because the symbolic link stores:

```text
/etc/hosts
```

as a pathname.

---

# Symlink vs Hard Link

| Feature                               | Symbolic Link                 | Hard Link                    |
| ------------------------------------- | ----------------------------- | ---------------------------- |
| Stores                                | Target pathname               | Reference to same inode      |
| Crosses filesystems                   | **Yes**                       | **No**                       |
| Crosses partitions                    | **Yes**                       | **No**                       |
| Can point to directories              | **Yes**                       | Usually not for normal users |
| Different inode from target           | Yes                           | No                           |
| Works if original filename is deleted | No, if target path disappears | Yes                          |
| Can point to missing target           | Yes                           | No                           |
| Target path visible with `ls -l`      | Yes                           | No                           |
| Created with                          | `ln -s`                       | `ln`                         |

---

# Hard Link Example

```bash
ln original.txt hardlink.txt
```

Architecture:

```text
original.txt
      │
      ├───────────┐
      ▼           ▼
        Same Inode
      ▲           ▲
      └───────────┘
      │
hardlink.txt
```

---

# Symbolic Link Example

```bash
ln -s original.txt softlink.txt
```

Architecture:

```text
softlink.txt
     │
     │ Stores:
     ▼
"original.txt"
     │
     ▼
original.txt
     │
     ▼
Inode
```

# 🔧 Troubleshooting

## Problem 1 – Symbolic Link Shows `No such file or directory`

Check:

```bash
ls -l LINK_NAME
```

Look at the target after:

```text
->
```

Verify that the target exists.

---

## Problem 2 – Target Filesystem Is Not Mounted

Check:

```bash
findmnt /boot
```

or for another filesystem:

```bash
findmnt /data
```

If the filesystem is not mounted, the symlink may exist but its target will be unavailable.

---

## Problem 3 – Hard Link Returns `Invalid cross-device link`

This usually means the source and destination are on different filesystems.

Check:

```bash
df SOURCE_FILE
```

and:

```bash
df DESTINATION_DIRECTORY
```

If they show different filesystems, use a symbolic link instead.

---

## Problem 4 – Relative Symlink Breaks After Moving It

Example:

```bash
ln -s file1 /tmp/my-link
```

Relative symbolic links are resolved relative to the directory containing the link.

For links across directories or filesystems, using the absolute target path is often easier to understand:

```bash
ln -s /data/files/file1 /tmp/my-link
```

Can a hard link cross filesystem boundaries?

**Answer:**

Why can't a hard link cross filesystems?

**Answer:**

**Answer:**

Yes.

**Answer:**

The symbolic link becomes a dangling or broken link.

Does deleting one hard-link filename delete the data immediately?

**Answer:**

No. The data remains as long as another hard link still refers to the inode.

It defines filesystems and where they should be mounted. It is not itself the mechanism that creates symbolic links.

# 📖 Key Takeaways

* Symbolic links can cross partitions and filesystem boundaries.
* Symbolic links work because they store a target pathname.
* The Linux VFS resolves paths across mounted filesystems.
* A symlink under `/etc` can point to a target under a separately mounted `/boot`.
* Symbolic links can point to both files and directories.
* A symlink can exist even when its target does not exist.
* Such a link is called a dangling or broken symbolic link.
* Hard links refer directly to the same inode.
* Hard links therefore must remain within the same filesystem.
* `/etc/fstab` defines where filesystems are mounted; symbolic links can then refer to paths within those mounted filesystems.

# 💡 Remember

> **Think of a symbolic link as an address written on a piece of paper.**

The address can point anywhere in the mounted Linux filesystem tree:

```text
Symbolic Link
     │
     ▼
"/boot/grub2/grub.cfg"
     │
     ▼
Linux Follows the Path
     │
     ▼
Different Filesystem
     │
     ▼
Target File
```

A hard link is different:

```text
Hard Link
     │
     ▼
Same Inode
     │
     ▼
Same Filesystem Only
```

# ⭐ Golden Rule

```text
SYMBOLIC LINK
     │
     └── Stores a PATH
              │
              ▼
       Can Cross Filesystems
```

```text
HARD LINK
     │
     └── References an INODE
              │
              ▼
       Same Filesystem Only
```

Example:

```bash
ln -s /boot/grub2/grub.cfg /etc/grub2.cfg
```

works even when:

```text
/etc  → Root Filesystem
/boot → Separate Filesystem
```

because **symbolic links follow pathnames rather than being tied directly to the target filesystem's inode table.**
