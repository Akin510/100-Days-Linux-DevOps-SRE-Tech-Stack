# 📖 Introduction

In this lesson, we will look more closely at the architecture of:

```text
Nginx
```

and compare it with:

```text
Apache
```

Both can function as web servers, but they use different architectural approaches.

One of the most important differences is how they handle incoming client requests.

---

# Apache vs Nginx – Basic Architectural Idea

Conceptually:

```text
Apache
   │
   ▼
Process / Thread-Oriented Request Handling
```

while:

```text
Nginx
   │
   ▼
Event-Driven / Asynchronous Request Handling
```

This difference has a major effect on:

* Concurrency
* Memory usage
* Static content performance
* Resource utilization
* Scalability

---

# Apache Prefork Model

The lesson describes Apache using its traditional:

```text
Prefork
```

processing model.

In prefork mode, Apache creates multiple server processes.

Each process handles requests independently.

A simplified architecture looks like:

```text
Apache Parent Process
        │
        ├── Worker Process 1
        ├── Worker Process 2
        ├── Worker Process 3
        └── Worker Process 4
```

---

# One Request Per Process Concept

In the traditional prefork model, a worker process handles one request or connection at a time.

Conceptually:

```text
Client 1
   │
   ▼
Apache Process 1
```

```text
Client 2
   │
   ▼
Apache Process 2
```

```text
Client 3
   │
   ▼
Apache Process 3
```

As the number of simultaneous requests increases, Apache requires more processes to handle them.

---

# Apache Request Handling Example

Suppose Apache has four available worker processes:

```text
Apache
  │
  ├── Worker 1 → Client A
  ├── Worker 2 → Client B
  ├── Worker 3 → Client C
  └── Worker 4 → Client D
```

If another request arrives:

```text
Client E
```

it may need to wait until server capacity becomes available, depending on Apache's configuration and limits.

---

# Static and Dynamic Requests in Apache

In the model described in the lesson, Apache workers may handle different types of resources using the same process architecture.

Examples:

```text
Request 1 → PHP Script
Request 2 → Image
Request 3 → HTML File
Request 4 → CSS File
```

Each request consumes a worker.

This can create additional resource overhead when many simultaneous connections exist.

---

# Nginx Uses an Asynchronous Model

Nginx takes a different approach.

Nginx is designed around:

```text
Asynchronous
```

and:

```text
Event-Driven
```

request handling.

Instead of requiring a separate process for every connection, a single Nginx worker can manage many connections concurrently.

---

# Nginx Concurrency Model

Conceptually:

```text
                  Nginx Worker
                      │
       ┌──────────────┼──────────────┐
       │              │              │
       ▼              ▼              ▼
   Client 1       Client 2       Client 3
       │              │              │
       ▼              ▼              ▼
   Client 4       Client 5       Client 6
```

One worker process can manage many active connections.

---

# What Does Asynchronous Mean?

Asynchronous processing means that Nginx does not have to wait for one request to fully complete before managing another connection.

Conceptually:

```text
Request A
   │
   ├── Waiting for network/data
   │
Request B can still be processed
   │
Request C can still be processed
```

This allows Nginx to efficiently manage many simultaneous clients.

---

# Synchronous vs Asynchronous Concept

## Simplified Process-Oriented Model

```text
Worker 1 → Request 1
Worker 2 → Request 2
Worker 3 → Request 3
Worker 4 → Request 4
```

---

## Nginx Event-Driven Model

```text
One Worker
    │
    ├── Request 1
    ├── Request 2
    ├── Request 3
    ├── Request 4
    ├── Request 5
    └── Many More
```

The number of connections Nginx can handle depends on:

* System resources
* Nginx configuration
* Operating system limits
* Application architecture
* Network capacity

---

# Why This Matters

A web server may have thousands of users connected at the same time.

Example:

```text
Client 1
Client 2
Client 3
...
Client 5000
Client 10000
       │
       ▼
      Nginx
```

Nginx's design allows it to manage many connections without requiring one full process per client.

---

# Dynamic Content Is Different

Nginx itself does not normally embed server-side programming language runtimes directly into its worker processes.

Examples of server-side languages include:

* PHP
* Python
* Ruby
* Java

Instead, dynamic content is usually handled by a separate application process.

---

# Example – PHP with Nginx

A common setup uses:

```text
PHP-FPM
```

PHP-FPM stands for:

```text
PHP FastCGI Process Manager
```

The architecture looks like:

```text
Client
   │
   ▼
Nginx
   │
   ▼
PHP-FPM
   │
   ▼
PHP Application
```

---

# Dynamic PHP Request Flow

Suppose a client requests:

```text
/index.php
```

Nginx receives the request.

```text
Client
   │
   │ GET /index.php
   ▼
Nginx
   │
   │ Forward Dynamic Request
   ▼
PHP-FPM
   │
   ▼
PHP Executes Script
   │
   ▼
Response
   │
   ▼
Nginx
   │
   ▼
Client
```

Nginx acts as a reverse proxy between the client and PHP-FPM.

---

# Static Content with Nginx

Static resources can be served directly by Nginx.

Examples include:

* HTML

* JavaScript

* Videos
* Download files

Architecture:

```text
Client
   │
   │ Request image.jpg
   ▼
Nginx
   │
   ▼
Static File
   │
   ▼
Client
```

No PHP process is needed.

---

# Static vs Dynamic Request Flow

```text

   │

   │
   ▼

   │
   ▼

```

## Dynamic Request

```text
Client
   │
   ▼
Nginx

   │
```

# Why This Can Save Resources

Suppose a page contains:

```text
1 PHP Page
10 Images
3 CSS Files
5 JavaScript Files
```

There are:

```text
19 total requests
```

With Nginx, only the request that actually requires PHP needs to involve PHP-FPM.

Conceptually:

```text
19 Requests
     │
     ├── 18 Static → Nginx
     │
     └── 1 Dynamic → PHP-FPM
```

This is an important source of resource efficiency.

---

# Resource Separation

Nginx does not eliminate the resources required to execute PHP.

Those resources are still used by:

```text
PHP-FPM
```

The difference is that they are separated from Nginx's own web-serving processes.

Conceptually:

```text
Nginx
 │
 ├── Static Content
 ├── Connections
 └── Proxying

PHP-FPM
 │
 └── PHP Execution
```

---

# Separation of Responsibilities

```text
Nginx
   │
   ├── Receive connections
   ├── Serve static content
   ├── Proxy requests
   └── Manage HTTP traffic

PHP-FPM
   │
   └── Execute PHP code
```

Each component performs a specialized job.

---

# Why Nginx Uses Fewer Resources for Static Requests

A static request does not need to load or involve the PHP runtime.

For example:

```text
/image/logo.png
```

can simply be served by Nginx.

```text
Client
   │
   ▼
Nginx
   │
   ▼
logo.png
```

There is no need to involve:

```text
PHP-FPM
```

---

# Mixed Content Website Example

Suppose a website contains both:

```text
Static Content
+
Dynamic Content
```

A well-configured Nginx environment can separate these workloads.

```text
                     Nginx
                       │
        ┌──────────────┴──────────────┐
        │                             │
        ▼                             ▼
Static Files                    Dynamic Requests
        │                             │
        ▼                             ▼
Serve Directly                    PHP-FPM
```

This can improve resource efficiency.

actually means.


```text
1 Gbps
```

# Important Apache Nuance

Apache is not limited to prefork mode.

Modern Apache installations can use different:

```text
MPMs
```

MPM stands for:

```text
Multi-Processing Module
```

Common Apache MPMs include:

* `prefork`
* `worker`
* `event`

Therefore, the exact comparison depends on how Apache is configured.

The lesson is mainly comparing Nginx with the traditional Apache prefork model.

---

# Apache MPM Concept

```text
Apache
   │
   ├── prefork
   ├── worker
   └── event
```

This is important when making modern performance comparisons.

---

# Nginx Configuration Approach

Nginx configuration also differs from Apache configuration.

The lesson emphasizes that Nginx commonly interprets incoming requests based on:

```text
URI Locations
```

rather than focusing primarily on filesystem directories.

---

# What Is a URI?

URI stands for:

```text
Uniform Resource Identifier
```

For example:

```text
/images/logo.png
```

or:

```text
/api/users
```

or:

```text
/admin
```

Nginx can match requests based on these locations.

---

# Nginx `location` Concept

Example:

```nginx
location /images/ {
    ...
}
```

This means:

> Apply these rules to requests whose URI begins with `/images/`.

---

# URI-Based Request Handling

```text
Client Requests:
/images/logo.png
       │
       ▼
Nginx
       │
       ▼
location /images/
       │
       ▼
Apply Configuration
```

---

# Another Example

```nginx
location /api/ {
    proxy_pass http://backend;
}
```

Conceptually:

```text
Client
   │
   │ /api/users
   ▼
Nginx
   │
   ▼
location /api/
   │
   ▼
Backend Application
```

---

# Apache's Filesystem-Oriented Approach

Apache configuration commonly makes heavy use of filesystem directories.

For example:

```apache
<Directory "/var/www/html">
    ...
</Directory>
```

Conceptually:

```text
Filesystem Directory
/var/www/html
      │
      ▼
Apache Configuration
```

---

# Nginx URI vs Apache Directory Concept

| Nginx                       | Apache                                      |
| --------------------------- | ------------------------------------------- |
| Often matches URI locations | Often configures filesystem locations       |
| Uses `location` blocks      | Uses directives such as `<Directory>`       |
| Request-routing oriented    | Filesystem-oriented configuration is common |

---

# Apache `.htaccess`

Apache can allow directory-level configuration using:

```text
.htaccess
```

files.

Example:

```text
/var/www/html/.htaccess
```

These files can override certain settings for specific directories when Apache is configured to allow them.

---

# `.htaccess` Concept

```text
Apache Main Configuration
        │
        ▼
Website Directory
        │
        ▼
.htaccess
        │
        ▼
Directory-Specific Overrides
```

---

# Nginx and `.htaccess`

Nginx does not use `.htaccess` files.

Nginx configuration is normally managed centrally through its configuration files.

Conceptually:

```text
Nginx Configuration
       │
       ▼
Central Configuration
       │
       ▼
Request Processing
```

---

# Why Nginx Avoids Per-Directory Overrides

Per-directory configuration files can introduce additional processing because the web server may need to check for configuration overrides while traversing directories.

Nginx avoids this model.

This keeps its configuration architecture centralized.

---

# Performance Summary

When discussing Nginx performance, the important idea is not simply:

```text
Nginx sends bytes faster
```

Instead, its architecture can allow it to:

* Handle more concurrent connections efficiently.
* Serve static files with low overhead.
* Separate dynamic application processing from web serving.
* Use system resources efficiently under heavy load.

# 📖 Key Takeaways

* Nginx and Apache use different architectural approaches.
* The lesson compares Nginx primarily with Apache's traditional prefork model.
* Nginx uses asynchronous, event-driven request handling.
* A single Nginx worker can manage many concurrent connections.
* Nginx normally delegates dynamic language processing to separate application processes.
* PHP-FPM is commonly used to process PHP applications behind Nginx.
* Static resources can be served directly by Nginx.
* Separating static content from dynamic processing can reduce unnecessary overhead.
* Nginx performance advantages are especially noticeable under high concurrency.
* Nginx cannot overcome physical network bandwidth limits.
* Nginx configuration strongly emphasizes URI-based request routing.
* Nginx does not use `.htaccess`.
* Nginx can function as a web server, reverse proxy, load balancer, cache, and other types of proxy.
